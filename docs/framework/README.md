# Bot 框架：基础设置、内置能力与扩展资源

插件作者入口：[当前开发手册](../plugins/README.md)。独立迁移工作区为 `../pi-im-bot-plugins`，包含文档快照、公开 SDK 构建别名和首个系统状态迁移插件。

插件产品层已完成首批正式实现，见 [插件中心、配置与发布包](plugin-management.md)。[设计基线](plugin-center.md) 保留对 AstrBot/Koishi 的源码核对及早期原型，未实现部分以阶段记录为准。

状态：前两阶段、第三阶段及第四阶段 A—E 已实现并有主机 Bun 服务部署记录。包括共享会话、分层设置、Persona、消息投影、调用权限、单一工具收纳策略、HTTP MCP、Skill 包、durable 运行、合批、后台 Job/子 Agent、媒体/引用、发送账本、MCP Tasks、Cron，以及插件操作、共享切入点、持久观察、跨插件调用、schema 配置和插件安装管理。第四阶段 D 的硬容量持久卷、产物额度、流式发布和插件自定义切入点通过真实容器验收。执行默认关闭是新配置的默认值；2026-11-12 部署记录已启用，2026-11-13 只读诊断仍为 enabled:true。当前状态看在线 `/api/plugins/observers` 和运行环境诊断；旧阶段记录中的关闭状态只描述当时。实现范围见 [阶段交付记录](implementation.md)，未部署的审核修复见 [本轮报告](review-remediation-2026-11-12.md)。

异步与并发使用群主 conversation + 有界合批 + 后台 Job/子 conversation，已切换到官方 pi-durable 1.5.0。详见 [异步与同群并发](async-and-concurrency.md) 的设计依据及阶段交付记录中的实际范围。

群聊的 user 状态以群为单位共享。群员 ID、昵称和发言是消息来源信息；当前不按群员建立个人 Persona、记忆、偏好或 root conversation。后台会话按工作任务拆分。

群聊、私聊、WebChat 都以各自的聊天来源绑定当前 conversation；工具调用权限仍可受本轮触发人限制。参见 [会话范围与触发人权限](conversation-scope.md)，包括按来源核对的监控样例。

## 1. 当前需求基线

以 [实际配置与使用审计](runtime-baseline-2026-11-09.md) 为迁移依据，[安装目录盘点](installed-plugin-map.md) 作为功能索引。

- 33 个用户插件目录中，全局未禁用 22、禁用 11；profile 和插件自身范围还会过滤。
- 当前工具收纳由 Enishi 工作，Lazy Tools 与独立群流水关闭。收纳策略是单选能力。
- MCP 配置启用 9 个；Skill 有 14 个启用标记，需再核对来源、沙盒可用性与 Persona 绑定。
- 最近 7 天有 3007 次工具执行，主要涉及能力发现、沙盒、搜索、图像、子 Agent 和交付。
- 97 次子 Agent 转交中 85 次是后台模式；异步任务与回流属于实际基建需求。

前一版把安装目录中的复杂功能都作为第一阶段压力样例，扩大了当前范围。HAPI、PriceAI、绘画经验等已关闭功能保留为后续扩展参考，不决定当前 MVP。

## 2. 核心分为四类职责

| 类别 | 回答的问题 | 应由框架提供的设置/机制 |
| --- | --- | --- |
| 数据加工 | 给模型和下游什么数据、以什么形态提供 | 消息规范化、引用展开、图片 ID/像素投影、群流水增量、工具结果裁剪/归档、历史压缩、输出清理 |
| 偏好 | 希望助手如何表达、默认使用什么 | 人格、语言/语气、回复样式、音色偏好、默认模型/工作流、不同会话的资源偏好 |
| 行为 | 何时做、由谁做、怎么执行与反馈 | 唤醒/@/指令、群开关、自身消息、流式/仅最终、主动通知、同步/后台委派、超时、重试、取消、分段发送 |
| 内置基建 | 这些行为依靠什么可靠运行 | IM 适配、Pi runner、会话/消息存储、沙盒、模型网关、能力目录、MCP 客户端、Skill/KB 接入、调度、任务、产物/回执、观测和配置管理 |

这些属于 Bot 的产品配置和稳定接口，不要求用户为每个小开关安装一个插件。相同字段有确定的生效位置与来源，默认不暴露一套任意可重排的内部流水线。

### 数据加工

保留原始消息/事件、持久会话事实、单次模型上下文投影、用户可见输出四个视图。数据微调发生在相应投影中，不随意覆盖原始记录。

当前配置中的身份/群名/时间信息、引用链深度、图片本轮放行、群流水增量、历史字符预算、工具结果收纳，都是该类设置。字符限制、估算 token、provider 返回的 usage 是不同单位。

Pi 继续负责原生会话与压缩；Bot 提供额外上下文及清理规则。统一保留来源、scope、引用和寿命，避免把临时像素或长工具原文重复带进后续轮次。

### 偏好

人格是有版本的资源，绑定到群的运行配置/会话；群员画像是上下文资料，不自动成为另一份人格或 user 状态。工具、Skill、知识库和模型组等资源偏好由该群共享。

按默认、账号、群/话题、会话和本轮覆盖解析，字段声明允许的覆盖范围；当前不增加群员个人偏好层。界面显示最终生效值及来源。null、空集合、继承和“全部可用”使用明确语义，避免无意扩大或清空能力。

### 行为

规则使用确定性代码执行，参数可配置。例子包括普通消息是否只记录、哪些指令直接处理、空 @ 是否等待、自身消息是否参与、是否展示工具过程、后台任务完成后直接发送还是交给主 Agent 整理。

行为设置与基建实现分开：选择“后台委派”会调用任务服务，不直接把一个 Promise 挂在消息钩子里。选择“仅最终回复”使用明确输出阶段，不包装 Pi 私有 step。

### 内置基建

在现有 Bun/Hono/Zod 栈上逐步抽取服务，不先拆成许多独立部署：

- Channel、Message、Conversation、Artifact、DeliveryReceipt。
- 指令分发、会话状态与有界交互，例如批量撤回确认；已有明确授权不重复确认。
- Profile/Persona 与有效配置解析。
- Pi Bridge、Model Gateway、现有 Provider 候选组及请求级 fallback。
- 能力目录、单一工具收纳策略、MCP/Skill/知识库访问接口。
- 现有 Shipyard 适配、任务/子 Agent、Cron、结果回流和主动交付。
- 异步操作的统一受理/状态/完成协议；群主对话单 run、后台任务并发，任务关联与定向取消。
- 结构化 trace、用量、超时、取消、队列和资源限额。

现有 Agent 容器内自由执行的约定保持不变。文件与 Shell 不回退宿主机。是否需要更强运行时安全隔离属于独立部署议题。

## 3. 扩展资源是独立的可配置对象

| 资源 | 职责 | 配置重点 |
| --- | --- | --- |
| 插件 | 增加业务代码、指令、工具、服务、页面或必要的扩展处理器 | 版本、实例、启用范围、私有数据、依赖和资源额度 |
| MCP | 接入远程工具服务 | 连接、凭据、健康、工具目录与 scope；当前先覆盖实际使用的 HTTP transport |
| Skill | 提供按需加载的说明、脚本和资产 | 来源、版本、启用、Persona 绑定、guest 路径和可用性 |
| 知识库 | 提供检索数据 | 集合、内容状态、embedding/rerank、检索方式与 profile 绑定 |
| Provider | 提供聊天、视觉、embedding、语音/图像等模型服务 | 连接与模型分层、用途/能力、headers/body、候选顺序和失败策略 |

Provider 的资源配置层保留已实现的网页功能；不会因框架分层而推迟实际 LLM 接入。其他资源按使用优先级接入。

这些对象不是同一种可执行插件。例如 MCP 管理插件关闭，不代表 MCP 服务关闭；Skill 开关打开，不代表资源路径存在；知识库有名字，不代表有文档。

所有资源具有清晰状态链：

~~~text
已安装/登记 → 配置启用 → profile/Persona 选中
           → 来源可用 → 本轮已装载 → 实际调用/检索
~~~

设置界面应能显示各层原因，而不只展示一个“已启用”布尔值。

## 4. 工具收纳使用一个选定策略

同一有效运行配置选一个工具暴露/收纳实现，例如全量或当前的紧凑目录策略。保留 Enishi 的有效机制与必要参数，优先通过 Pi 公共能力实现，不逐行移植其 AstrBot patch，也不实现多个收纳插件并行竞争。

能力目录可以汇集内置工具、插件工具、MCP 工具和 Skill；负责收纳/暴露的策略只有一个。收纳状态按会话/Agent 隔离，策略切换在清晰的轮次边界生效。

可调项包括常驻集合、按需分组、闲置轮数、Skill 折叠、结果归档、描述和预算。目录 ID 稳定，显示名和模型别名与实际实现分开，避免加载了名字相同但来源不同的工具。

授权集合、可用集合和本轮暴露集合分别计算。隐藏/折叠不是权限撤销，资源停用也不能被“加载工具”重新开启。

## 5. 插件与内置设置的边界

现有插件按功能拆解，不机械地一对一搬迁：

- 空行整理、过程可见性、群 LLM 开关、频道默认配置等，适合成为内置参数或策略。
- Enishi 的数据投影、目录收纳与资源寿命，适合进入基建和选定策略。
- 监控所需的关键事件由核心产出，监控页面或分析可扩展。
- 生图、B 站业务、特殊图像处理等领域逻辑，继续作为插件或外部服务。
- 同一功能可以横跨几层：音色是偏好，何时转语音是行为，媒体/发送是基建，语音引擎是资源。

插件内部自由组织业务、依赖和私有数据。需要影响框架或其他插件时，使用公开服务或已定义的切入点，不能修改另一个插件实例。

优先级只用于确实共享的扩展点，例如额外文本变换、领域请求准备、平台负载兼容；内置设置无需全部变成可排序插件。按 point 定义追加、变换、选择、观察等语义，再支持 priority 和 before/after。

详细的 [扩展契约](extension-contract.md) 与 [状态/生命周期设计](state-and-lifecycle.md) 保留为后续实现参考。它们不是要求第一版一次性实现所有插件模式。

## 6. 配置与运行结构

~~~mermaid
flowchart TD
  SETTINGS["Bot 设置：数据加工 / 偏好 / 行为"] --> PLAN["解析有效运行配置"]
  LIBRARY["资源库：插件 / MCP / Skill / KB / Provider"] --> PLAN
  INFRA["内置基建：IM / 存储 / Pi / 沙盒 / 调度 / 交付"] --> RUN["执行与观测"]
  PLAN --> RUN
  RUN --> RESULT["消息、产物、任务结果与真实回执"]
~~~

每轮使用固定配置/人格/资源版本，权限撤销与取消实时检查。原始消息、模型投影和输出呈现仍保持独立。

UI 建议按三组组织：

1. Bot 设置：数据、偏好、行为；选择作用域并查看生效来源。
2. 基础能力：执行环境、上下文与收纳、任务/子 Agent、交付、观测。
3. 资源管理：插件、MCP、Skill、知识库、Provider；分别管理启用、绑定与健康。

高级扩展点与优先级放在需要该能力时的高级配置中，不作为普通用户调整音色、模型或回复格式的必经入口。

## 7. 按实际使用推进

| 顺序 | 交付范围 | 实际验证依据 |
| --- | --- | --- |
| 1 | 设置模型、作用域、Persona、数据/输出视图和资源引用 | 当前多个档案、会话覆盖、图片/引用/分段规则 |
| 2 | 单一收纳策略、稳定目录、MCP 与 Skill 基础加载、沙盒文件链路 | 7 天目录调用 584、沙盒/文件 632、搜索/抓取 564；实际 Skill 加载链 |
| 3 | 视觉/媒体、异步子 Agent、Cron、任务回流、产物交付 | 图像链 605、图片理解/取图 194、后台转交 85、发送工具 167 |
| 4 | Skill 包管理与资源健康、知识库绑定与检索、领域插件迁移 | 当前启用资源与实际加载/检索记录；低频被动能力另按配置验收 |
| 后续 | HAPI 等外部会话、PriceAI 等外部可靠订阅、复杂插件工作流 | 由后续启用需求决定，不再作为当前内核门槛 |

运行逻辑先复用 Pi 的公共 SDK、现有 Provider 和 Shipyard。MCP/Skill/KB 的注册与配置是不同资源适配，不另造第二套 Agent 引擎。优先级、规则、装配和回执处理不额外调用 LLM。

pi-durable 已提供大量 conversation/task/document 机制。若接入核验通过，应复用这些机制，通过 Runner/ExecutionEnv 适配当前能力，而不再重复建设同一层状态机。
