本阶段完成包快照、注册表、Worker RPC、宿主服务授权边界和顺序变换执行器。以下以第四阶段 A 的交付记录为主；操作、工具、指令和 Web 管理由 [第四阶段 B](plugin-integration.md) 接入，实际交付钩子见 [第四阶段 C](plugin-pipeline.md)，硬容量存储与真实容器验收见 [第四阶段 D](plugin-storage.md)。该阶段验收时正式插件执行关闭。

## 包与资源版本

插件目录含 `plugin.json`，入口为已经构建的 `.js` 或 `.mjs`。声明 `files` 的文件才会进入快照；导入不运行入口、安装脚本或构建脚本。TypeScript 作者可在自己的开发目录预先构建，再登记输出目录。

- 一个包最多声明 2000 个文件，单文件 16 MiB，总量 64 MiB，manifest 最多 1 MiB。
- 文件与中间目录拒绝符号链接，只读取普通文件，读取期间增长的文件不会被无界载入内存。
- 快照按内容摘要保存在 `plugins/<instance>/<revision>/`，每次建立 Worker 前核验。来源目录变化不会覆盖旧版本。
- `package-index.json` 属于框架保留路径。文件清单、摘要、路径和 manifest 必须一致。
- 实例配置、代码 revision 和群范围是不同概念。编辑 MCP/Skill 资源保留已有插件目录；私有配置快照也保存插件包描述，以供后续任务恢复。

插件模型能力使用 `plugin:<instance>/<operation>`，指令能力使用 `command:plugin:<instance>/<command>`。模型别名独立生成；同名 operation 不会覆盖另一个实例的工具。当前只是目录和契约，不代表工具已经装载进 Pi。

## 执行与数据结构

准备的部署结构为：

```text
pi-im-bot/                            Bot 主体
plugins/<instance>/<revision>/        固定插件代码
plugin-data/<deployment>/<instance>/<scope>/
                                     插件的群级持久数据
data/plugin-runtime/                 受管入口、临时 RPC socket
```

Worker 以实例、版本、聊天范围定位。同一群所有成员使用同一份插件数据；成员身份仅作为本次调用来源和授权输入。不同群、不同实例使用不同目录。

同一实例、同一聊天范围的调用串行访问私有数据；不同插件及范围可并发。升级版本保留数据，在挂载同一数据目录给新版本前回收旧 Worker，避免两个版本同时写同一目录。数据格式迁移仍由后续插件生命周期协议处理，不自动保证跨版本的数据兼容性。

计划中的 Docker Worker 挂载只有：

| 容器路径 | 内容 | 权限 |
| --- | --- | --- |
| `/plugin` | 本实例的固定代码快照 | 只读 |
| `/runner` | 框架构建的受管入口 | 只读 |
| `/rpc` | 此 Worker 的 Unix socket | 只读挂载 |
| `/data` | 此实例、此聊天范围的数据父视图 | 只读 |
| `/data/files` | 固定容量文件系统，`context.dataDir` | 可写 |

根文件系统只读，`/tmp` 是 64 MiB tmpfs，网络关闭，移除 capabilities，禁止提权，不挂载 Docker socket、Bot 配置或其他插件目录。不继承宿主环境；受管入口关闭 Bun 自动依赖安装和 `.env` 自动加载。镜像需要预先存在，启动时解析到镜像 ID，不自动拉取。

默认额度：4 个业务 Worker，另有 1 个纯 schema 验证名额，64 个额外排队调用，每业务 Worker 256 MiB 内存、0.5 CPU、64 个进程。第四阶段 D 已将普通数据 bind 改为固定容量文件系统，默认每卷 64 MiB、每插件 1 GiB、全局 8 GiB；真实容器验收通过，正式启用仍需准备部署依赖。

直接运行和 Bot 自身位于 Docker 内时分别使用本地路径及 `hostPackageDir` / `hostDataDir` / `hostRuntimeDir` 映射。Docker 控制权属于受信宿主运行时，不提供给插件。工作区的容器授权规则仍适用于实际部署，日志中的容器变更通知不代替用户授权。

## RPC 和故障边界

连接使用长度帧和独立握手凭据，单帧最多 512 KiB，每次调用收发各最多 32 MiB，默认最多 256 次宿主 RPC。分片帧按长度读取，超大声明在分配相应缓冲区前拒绝；发送缓冲超过预算时终止连接。

宿主方法只有在三个条件都满足时执行：操作声明需要、实例配置允许、本次调用获准。服务绑定可信的 invocation，方法参数经各自 schema 校验；它们不能另行选择群号或高权限发言者。每次调用前仍执行框架提供的实时授权检查。当前提供此调度接口，没有注册具体历史、存储、连接器或发送服务。

- 同一次 RPC 请求 ID 和相同参数复用原结果；ID 相同但参数不同会拒绝。这是单次调用内的去重，尚不是跨重启的副作用账本。
- 调用具有包含排队时间的硬期限和取消信号。Worker 卡死、断连、协议错误后回收；正常业务错误不会直接熔断整个实例。
- 嵌套调用不等待一个正在使用的 Worker 或已耗尽的名额；环路和超过 8 层的嵌套会拒绝，避免插件持有名额互等。
- 回收异步进行，超时返回不等待 Docker 删除完成。未确认回收的 Worker 继续占用名额，清理失败在状态中保留，避免假装资源已释放。
- 重启清理和删除核对部署标签与精确容器名称，不修改其他服务容器。

这里的宿主服务方法只接受框架注册，不接受插件动态传入函数。自有外部调用、异步句柄、结果恢复和发送账本的接入安排在下一阶段。

## 共享切入点

注册表支持版本化核心切入点和插件发布的命名空间，校验处理器模式、独占槽、指令别名、依赖和字段声明。同一切入点先满足 `before` / `after` / `requires`，再按 priority 降序选择；同值按稳定 ID 排序。群设置可覆盖优先级和停用项，不能用优先级绕过依赖或扩大可写范围。

目前可实际执行的是 `transformPluginPoint` 顺序变换：

1. 每个处理器接收前一份有效数据的副本及 `inputRevision`。
2. 返回一份带 `baseRevision` 的 patch。
3. 框架检查 point 允许的字段、handler 更窄的 `writes`、版本和完整结果 schema。
4. 全部通过后才提交。包含一个越权字段、错误类型或过期版本时整份 patch 丢弃，前面合法的修改也不保留。
5. 允许跳过的失败沿用上一份有效数据，依赖失败处理器的后续步骤也跳过；`onError: fail` 停止此条流程。调用方取消始终停止，不能按 skip 继续发送。

数组元素删除会移动后续元素，所以要求拥有整个数组的写权限。JSON Pointer 转义按实际字段比较，原型字段、非法转义和越界索引不可写。

核心已经声明 `context.collect@1`、`delivery.visibility@1`、`delivery.text@1`、`delivery.presentation@1`、`delivery.receipt@1`、`message.recorded@1` 的元数据。除顺序变换执行器外，collect、policy、select、observe 的运行及实际 Bot 调用时机仍待接入；不能把这些元数据当作已经工作的发送/观察流程。
